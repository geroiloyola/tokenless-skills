# design-review

Read `references/uiux.md` (in this skill's folder) for the full digest: priority
table 1-10, token set, style families, seed palettes, font pairings, query
contract. The searchable catalog lives in the upstream skill if installed.

## Before coding (2 minutes, no exceptions)
1. Name the product type, the audience and the ONE feeling the page must convey.
2. Commit to one direction and write it down in the task: reference, mood, density.
   Generic means no decision was made. "Modern with purple gradients" is not a direction.
3. Derive tokens first, then components: background, surface, text, muted, accent,
   danger, success, plus a 4/8px spacing scale, a modular type scale, and one radius set.
4. Every color must exist as a token. No raw hex in components.
5. If the upstream skill is present, query it for the chosen
   product type and style; use its palettes and font pairings as the starting data.

## Hard rules (CRITICAL)
| Area | Must | Never |
|---|---|---|
| Accessibility | Text contrast ≥4.5:1, visible focus, labels, alt text | Remove focus rings |
| Target size | ≥44×44px interactive, ≥8px gap | Icon-only buttons without name |
| Responsive | Mobile-first, no horizontal scroll, 375px works | Disable zoom, fixed px containers |
| States | loading, empty, error, disabled for every async view | Ship only the happy path |
| Type | Body ≥16px, line-height ≥1.5, ≤75ch | Gray-on-gray text |
| Motion | 150–250ms, reduced-motion respected, animate transform/opacity | Animate width/height, one duration for all |
| Icons | SVG set, one family | Emoji as icons |
| Content | Real copy, real data | Lorem ipsum, placeholder avatars |

## Audit after building
Open the result in a browser (use the webapp-testing skill) at 375 and 1440. Score out of 10
on: hierarchy, spacing rhythm, contrast, state coverage, consistency of tokens.
For **contrast verification**: run `node <skill-dir>/scripts/contrast.mjs --fg=<hex> --bg=<hex>` for each token pair; mark PASS if ratio >=4.5. Otherwise: NOT AUDITED.
Anything ≤6 means fix it before finishing. Screenshot both widths as evidence.

## Output
`direction | tokens used | contrast checks | widths verified | score /10 | fixes applied`

description: "Measures whether changes to skills, AGENTS.md, hooks or agent configs improved the agent, by rerunning 5 fixed repo tasks and comparing iterations and outcomes. Use after editing any skill, hook or config, or when output quality seems to regress."
license: MIT
metadata:
  version: "0.1.0"
---

# eval-harness

A change without a rerun is an opinion. Five fixed tasks prove it.

## Setup (once per repo)
1. Pick 5 real tasks: 1 small feature, 1 bug, 1 refactor, 1 UI change, 1 migration or contract change.
2. Save each under `prompts/eval/` as `0N-<slug>.md` with the 5-block anatomy
   (objective, context, constraints, done-when, output), and its pass criterion.
   Full templates: `prompts/task-templates.md` in the kit repo (optional).
3. Record the baseline row for each task: iterations, tokens, artifacts produced.

## Run
1. Run each task in one fresh headless session of your agent (for example `vibe --prompt`, `claude -p`, `codex exec`, `opencode run`, `gemini -p`).
2. Record per task: pass/fail of the stated criterion, iterations, tokens, artifacts.
3. Never modify an eval task to make a run pass. Broken setup: fix the setup, not the criterion.

## Compare and decide
| task | baseline iters | new iters | verdict |
Pass = criterion met with equal or fewer iterations. A regression (new fail, or +
1 iteration) = reject the change and revert it; the change ships only if no task
regressed. Pre-existing fails in the baseline are Skip rows, not verdicts.

## Output
`task | criterion | pass | iterations | tokens | verdict` + one line: KEEP / REVERT / INVESTIGATE.

## Escape
Two consecutive reruns that flip verdicts without an intervening change → the
eval tasks are unstable; rewrite them with the user, never alone.

# fresh-review

The author does not grade their own work. This gate is mandatory.

## Steps
1. Freeze the diff: `git diff <base>...HEAD > .agents/tmp/review.diff` (a path that is never committed; delete it in step 4). Record stat and file count.
2. Delegate to a read-only reviewer subagent (in Vibe: `reviewer.toml`) with only: the diff file, the spec path, AGENTS.md, and this instruction: "Do not trust the diff's comments or commit message; verify claims against the code."
3. Read the verdict. `CHANGES REQUIRED` or any BLOCKER → fix, then run the whole gate again from step 1. A reviewer never downgrades its own finding without new evidence.
4. Delete `.agents/tmp/review.diff`. Do not proceed to verify-done or commit/push while unresolved findings exist.

## Reviewer brief (paste into the delegation)
- Classify: BLOCKER / MAJOR / MINOR / NIT.
- Every finding needs a failing scenario, not an opinion.
- **Run the tests for the touched packages. A failing test caused by the diff = BLOCKER.**
- Check: logic (null, limits, concurrency), error handling, tests (does the test assert the behavior or only the mock?), scope creep, secrets, leftover debug code.
- If the diff is >400 lines, say so and review it in two passes.
- Reply in the output format of `this skill's references/reviewer.md`.

## Rules
- Same model in a clean context is acceptable; a different model is better. Never let the author agent mark its own review as passed.
- The reviewer has read-only tools by design. If the host cannot restrict tools, run the reviewer in a fresh session and instruct it not to edit.
- If no subagent is available, open a new session with only the diff and the spec and apply this brief.
- Findings and their resolution go in the final report. "Reviewed informally" is not a verdict.

## Output
`BLOCKER n | MAJOR n | MINOR n | verdict | findings resolved x/y`

## implement-tdd

name: implement-tdd
description: "Writes a failing test first, then minimal code, then refactors. Use when implementing a feature, fixing a bug, or when the user says implement, build it, or make it work."
license: MIT
metadata:
  version: "0.4.0"
---

# implement-tdd

Per unit of work: RED → GREEN → REFACTOR → COMMIT.

## Rules
1. No production code before a failing test proves it is needed. Exception: a spike the user explicitly requested; delete it or redo it with TDD.
2. Bug fixes: reproduce with a failing regression test first. A bug without a regression test is not fixed.
3. "Minimal" = the simplest code that makes the test pass. If the test needs 3 methods, write 3, not 5 "just in case". If it needs no abstraction, add none.
4. One change, one commit. Never mix a refactor with a feature.
5. Never delete, skip, or weaken a test to get green. If a test looks wrong, say why and ask.
6. Do not touch files outside the plan. Report every deviation at the end.
7. Before each commit run build + lint + typecheck when the repo has them. Failures caused by your change: fix. Pre-existing failures: report, do not fix as a side effect.
8. An "attempt" = one code edit plus one test run. After 2 failed attempts on the same error, stop and run the systematic-debugging skill. Do not keep guessing.

## Test level by layer
| Layer | Minimum test |
|---|---|
| Function / logic | happy path + 2 edge cases |
| API endpoint | status, body, error path, validation |
| UI component | render + main interaction; snapshot only for stable layout, never for dynamic data |
| Data migration | up + down + existing rows |
| External service | contract test using fixtures copied from the real API |

## Steps
1. Read the task, the affected files, and AGENTS.md. **Language-specific test commands**: see `references/tests.md`.
2. Write the smallest test that captures "done".
3. Run only that test. Paste the real failure output; never claim a failure you did not see.
4. Implement the minimum. Run the test. Iterate to green.
5. Run the full suite of the package that contains the files you changed. In a monorepo use the workspace command from AGENTS.md (pnpm -F <pkg>, yarn workspace <pkg>, cargo test -p, pytest <path>).
6. Commit with the repo's convention; the body states why.
7. Update the todo list, then start the next task.

## Closing report
- Done: task ids + commit hashes
- Tests: new / modified, full suite result
- Deviations from the plan and the reason
- Next: next task, or "run the verify-done skill"

# learn-instinct

One instinct = one trigger + one action + confidence.

## Steps
1. Write the instinct in this format and append it to `~/.agents/memory/instincts.md`:
   `- [0.5] scope:global|repo:<name> | when: <situation> | do: <action> | domain: <lang/framework> | evidence: <where it worked> | expires: <date>`
   `expires:` only for instincts tied to a tool version or a workaround (set 30-90 days out); omit for stable patterns.
2. Start at 0.5. Same pattern worked again → add 0.1 (cap 0.9). It failed → subtract 0.2.
3. Delete anything at or below 0.2 or expired. Do not keep dead weight.
4. At 0.7+ with evidence from 2+ sessions, propose promotion:
   to `~/.agents/memory/lessons.md` as a rule, or to the repo AGENTS.md if it is project-specific. Ask before promoting.
5. Keep the file under 40 lines. Prune lowest confidence first.
   **On session start, load only instincts with matching scope (global or current repo).**

## Quality bar
- Reject instincts that restate the framework docs, obvious language rules, or a one-time workaround.
- Reject instincts that are not falsifiable: if you cannot say when it should NOT apply, rewrite it.
- Never record secrets, customer data, or anything that changes per environment.

## If ECC is installed
Use ECC's continuous-learning-v2 instead (`/instinct-status`, `/evolve`, `/prune`), which stores instincts with project scope and confidence. Keep this file only as a fallback when ECC is not available; never maintain both in parallel.

# remember-correction

A correction is a bug report against your behavior. Fix it permanently.

## Steps
1. Stop the current approach. Restate the correction in one line and confirm it is understood.
2. Grep `~/.agents/memory/lessons.md` and the repo AGENTS.md. If a rule already covers it, tighten that line instead of adding a duplicate.
3. Append one line to `~/.agents/memory/lessons.md` (create the file if missing):
   `- YYYY-MM-DD | priority:HIGH|MEDIUM|LOW | scope: global | rule: <imperative, ≤15 words> | why: <what went wrong>`
   Use `scope: repo:<name>` for rules that only apply to this project. `expires: <date>`
   goes last, only for rules tied to a temporary workaround or a dependency version.
4. Re-read the line you wrote and check it is actionable by a different agent with no context.
5. Confirm to the user with the exact line, no explanation.

## Do not record
- One-off task preferences, secrets, or anything already in AGENTS.md.
- Vague lessons ("be more careful"). If you cannot state a concrete action, ask one question and record the answer.

## Housekeeping
Keep the file under 80 lines: merge duplicates, delete rules the repo has since encoded, keep the newest phrasing. The file is loaded at session start via AGENTS.md, so every line costs tokens in every session.

## If ECC is installed
ECC's continuous-learning handles this. Still write the line here: it survives plugin updates and is readable at a glance.

## repo-context
---
---
name: repo-context
description: "Creates or updates AGENTS.md with verified commands, repo map and canonical patterns. Use in an unfamiliar repo, before a first task there, or when the agent keeps breaking project conventions."
license: MIT
metadata:
  version: "0.4.0"

# repo-context

Produce an AGENTS.md the agent can trust: facts verified, no prose.

## Steps
1. If AGENTS.md exists, switch to update mode (step 5). Otherwise create it.
2. Read in plan mode: 2–3 levels of the tree, package manifest, lockfiles, README, lint/test/CI config, and 3–5 representative files per layer.
   **Runtime**: check `asdf current <lang>` or `.tool-versions` first; fall back to `engines` in package.json or `.python-version`.
3. Verify every command before writing it. No verification, no line.
4. Write AGENTS.md with the template below, 60–120 lines maximum.
5. Update mode: diff each section against the current repo and report a table `section | stale | fix`. Apply only what the user approves; keep the team's wording.

## Template
```markdown
# AGENTS.md

## Project
One line: what it is, stack, pinned runtime (from .nvmrc / engines / .python-version).

## Language
Reply in the language the user speaks; keep code, comments and commit messages in English.

## Commands (verified)
- Install / Dev / Test / Test one file / Lint / Typecheck / Build

## Repo map
- `src/<layer>/` — responsibility in ≤10 words (3–8 entries)

## Canonical patterns (copy these, do not invent)
- UI component: `path/to/example.tsx`
- API endpoint: `path/to/example.py`
- Test: `path/to/example.test.ts`
- Error handling: <pattern + path>

## Hard rules
- 5–10 non-negotiables: naming, imports, state, where logic must not live.

## Do not
- Real traps only: edit lockfiles by hand, run migrations manually, touch `generated/`.
```

## Checks before delivering
- [ ] Every command exists or was executed.
- [ ] ≤120 lines; no section duplicated from the README.
- [ ] Example paths exist in the repo.
- [ ] Monorepo: root AGENTS.md holds global rules and links each package's own AGENTS.md.

## Output
The full file in one code block, plus a short list of facts you could not verify.

## security-review
---
---
name: security-review
description: "Checks a diff for secrets, injection, authz gaps, unsafe deserialization and risky dependencies. Use before merges touching auth, payments, user input, file uploads, or queries, or when the user asks for a security pass."
license: MIT
metadata:
  version: "0.4.0"
---

# security-review

Scope the diff first; dig only where data crosses a trust boundary.

## Steps
1. Map the diff: does it touch input parsing, auth, permissions, payments, uploads, SQL/NoSQL, HTML rendering, file paths, env vars, or dependency manifests? If none, say "no trust boundary in scope" and stop.
2. Secrets: `git diff --name-only --diff-filter=d | xargs -r grep -nE "sk-|api[_-]?key|secret|token|password|BEGIN .*PRIVATE" --` (diff-filter=d skips deleted paths so grep does not error). Check .env files are untracked and reasons for any new env var.
3. Injection: user input reaching SQL (concat/interp), shell, eval, innerHTML/dangerouslySetInnerHTML, template engines without escaping, path joins with untrusted segments.
   **CSRF**: forms without CSRF tokens or missing `SameSite=Lax` cookies.
4. Authz: every new endpoint has an auth check; object access verifies ownership, not only login state; no IDOR via sequential IDs; admin routes guarded server-side.
   **SSRF**: user input used in URLs for internal requests (fetch, axios, curl).
5. Data: mass assignment, unbounded queries, missing pagination on user-facing lists, error messages leaking stack traces or SQL.
   **Mass Assignment**: `update` endpoints without allowlist of fields.
6. Dependencies: new packages in the diff? report name, version, why; prefer existing deps. Run the repo's audit command only if it is already configured.
   **OWASP Top 10**: see `references/owasp.md` for full coverage.
7. Out of scope by default: Semgrep/CodeQL, pentesting, infra. Recommend them in the report if the risk justifies it.

## Rules
- Never fix by adding a sanitizer around badly-placed raw input; fix at the boundary.
- A finding without an exploit path is a MINOR, not a BLOCKER.
- Do not paste real secrets in the report; use the file:line and the prefix only.

## Output
`vector | file:line | exploit path | severity (BLOCKER/MAJOR/MINOR) | fix | verified`

## spec-brainstorm

name: spec-brainstorm
description: "Turns a vague feature request into a short spec with acceptance criteria and edge cases, asking questions first. Use when a request is ambiguous, when several designs are possible, or before write-plan on any new feature."
license: MIT
metadata:

# spec-brainstorm

Clarify, then write the decision down. No production code in this skill.

## Rules
1. Max 4 questions per round via ask_user_question, 2–4 options each, one marked "(recommended)".
2. "Whatever you decide" → decide, and record the decision plus the reason in the spec.
3. Trivial request (typo, copy change, obvious one-line bug) → say so and propose skipping to the fix.
4. Requirements you had to assume are labeled "assumed", never presented as confirmed.
5. **Every acceptance criterion must start with "The system shall..." or "When [X], then [Y]". Reject criteria that are opinions or non-observable.**

## Questions that matter (pick 3–4)
- Scope: what is explicitly out of this iteration?
- Flow: who uses it and the happy path in 3 steps?
- Data: source, missing data, corrupt data?
- Constraints: fixed stack, offline, permissions, i18n?
- Success: which command or action proves it works?
- Reversibility: is this a one-way door (migration, public API)? If yes, require more validation.

## Output
Save to `specs/<slug>.md` (respect the repo's docs folder):
```markdown
# <Feature>
## Context — why this exists, 2 lines
## Scope — includes / excludes
## Behavior — numbered flow + edge cases (empty, error, limit, permission, concurrency)
## Contract — inputs, outputs, errors, UI states, real table/endpoint names
## Decision — chosen option + rejected alternative and why
## Acceptance criteria
- [ ] The system shall <observable action> when <condition>
- [ ] When <input>, then <output>
## Risks — max 3, each with a mitigation
## Open — unanswered questions; empty means the spec is ready
```

## Close
Rewrite any acceptance criterion that is an opinion into an observable check. Show the spec and ask: "Approve and continue to write-plan?" Wait for an explicit yes.

## subagent-execute

name: subagent-execute
description: "Executes plan tasks one at a time in isolated worktrees so the main session keeps a clean context. Use for multi-task plans, long autonomous runs, or when the user asks to run the whole plan, parallelize tasks, or work in a worktree."
license: MIT
metadata:
  version: "0.4.0"

# subagent-execute

One task per worktree. The main session plans and reviews, never edits.

## Steps
1. Pick the next pending task from `specs/<slug>-plan.md`. Tasks with `touches:` labels that share a file never run in parallel; if the plan omits `touches:`, derive it from the task's Files list.
2. Create an isolated tree:
   `git worktree add ../wt-<task-id> -b task/<slug>-<task-id>`
   If git worktree is unavailable (Web sandbox): run tasks serially in the main
   worktree, one task = one commit on one branch; isolation comes from serial
   execution, not the filesystem. No parallelism in this mode.
3. Spawn a subagent with this prompt:
   ```
   Work only in <worktree path>. Read AGENTS.md there.
   Task: <full task block from the plan>.
   Follow the implement-tdd skill. Run the single-file test, then the package suite.
   Commit with the repo convention.
   Reply only with: status, commit hash, tests run, files touched, deviations.
   If unsure about a requirement, stop and reply BLOCKED with the question.
   Do not touch files outside the task.
   ```
4. While it runs, keep working on independent tasks only if they share no `touches:` files.
5. On reply: run verify-done-style gates in that worktree, then merge `task/<slug>-<task-id>` into the base branch with `--no-ff`, one branch at a time; if the base moved, rebase the task branch first.
6. Close out: `git worktree remove ../wt-<task-id>`. The branch, and any push of the base branch, require the user's explicit approval — never push on your own.
7. If BLOCKED: answer the question or escalate to the human. Never let the subagent guess.

## Rules
- The main agent does not implement in this mode; if it starts editing, the mode is broken.
- A subagent gets one task, no backlog, and never sees the whole plan beyond its block.
- Every merge requires green gates in the worktree. A red task does not merge.
- Context budget: the subagent's transcript never enters the main session; only its 5-line report does.
- Parallel only when `touches:` sets are disjoint. When in doubt, serialize.

## Output
`task | branch | commit | gates | merged? | deviations` — one row per task, plus the final branch state.

## systematic-debugging
---
---
name: systematic-debugging
description: "Finds root causes with falsifiable hypotheses instead of random edits. Use for flaky bugs, unexplained test failures, production stack traces, or after two failed attempts at the same error."
license: MIT
metadata:
  version: "0.4.0"
---

# systematic-debugging

Reproduce → isolate → hypothesize → instrument → fix cause → verify.

## Steps
1. Reproduce with the exact command, input, runtime and flags. Intermittent: run N times and record the failure rate. No reliable repro: stop and build one, including a failing test.
2. Read the trace bottom-up (cause first) and find the first frame that is your code, not the framework's.
3. Isolate by bisection: disable half the flow, keep the half where it fails. `git bisect` if it regressed between commits. Shrink config, data and steps to the minimum that still fails.
   **For race conditions**: use the real detector of the runtime — `go test -race`, ThreadSanitizer (`-fsanitize=thread`) for C/C++, `jcstress` for the JVM; in JS, force interleaving by injecting `await new Promise(setImmediate)` between operations. Do not rely on repeated runs.
4. Write one hypothesis in this shape before touching code:
   `H: fails because X. Prediction: <probe> will show Y. Test: <command or log>.`
   One hypothesis at a time. Prediction false → hypothesis dead, next one. No fix without a hypothesis.
5. Fix the root cause with the smallest change. Add a regression test and prove it fails without the fix (revert in place). Grep for sibling occurrences of the same bug and cover null, empty, limit and concurrency variants.
6. Run the full suite plus the affected E2E flow.

## Stop signs
- 3+ attempts and the error changes shape but never disappears.
- You start swallowing exceptions or silencing warnings.
- 3+ files touched with no confirmed hypothesis.
→ Stop, write 5 lines of what you learned, return to step 1 or 3.

## Output
Cause in one sentence · evidence (hypothesis + result) · fix diff · regression test · lesson: what would have caught this earlier (test, type, validation).

## verify-done
---
---
name: verify-done
description: "Runs build, typecheck, lint and tests, then reviews the full diff against the spec before declaring work finished. Use before a final commit, a push, or opening a pull request."
license: MIT
metadata:
  version: "0.4.0"
---

# verify-done

"Done" means verified, not believed.

## Gates (run in order, keep the output)
0. **Performance (optional)**: only if the repo ships a real benchmark (script in package.json, `cargo bench`, pytest-benchmark) or records one in AGENTS.md: run it and compare to the last recorded baseline. Regression ≥5% = MAJOR. No baseline: skip and name it as skipped — never invent numbers.
1. typecheck (cheapest failures first)
2. lint
3. unit tests
4. tests of the affected package
5. build

Any failure: fix and restart from the gate that failed. Pre-existing failure (confirm with `git stash` if unsure): report it, do not fix it here.

## Diff review
Read `git diff --stat`, then the entire `git diff`, file by file.
- [ ] Changes outside the spec's scope? Revert them.
- [ ] Debug leftovers: console.log, print, dbg!, new TODO, sleeps, commented code?
- [ ] Secrets, tokens or .env content in the diff?
- [ ] Lockfiles or generated files changed by accident?
- [ ] Untracked files left behind (git status)? Artifacts from this run (screenshots, diffs, JSON) are outside the repo or deleted.
- [ ] Names and style match the repo's canonical patterns?
- [ ] Error paths handled: null, empty, timeout, permission denied?

## Spec check
| Acceptance criterion | How verified | Pass |
|---|---|---|
| ... | test X / manual step Y | ✅/❌ |

An unchecked criterion is not done. "Should work" is not a verification.

## Smoke (if UI or a user flow changed)
Start the project, walk the happy path plus one error case. Capture output or screenshot as evidence.

## Final report
- Status: READY / READY WITH PENDING ITEMS / NOT READY
- Gates: results per gate, test count
- Criteria: X/Y verified
- Pending: known risks
- Diff: N files, +A/−B, all within scope

Anything not green means the status is not READY.

## webapp-testing
---
---
name: webapp-testing
description: "Drives a real browser to verify UI rendering, console errors, network failures and basic accessibility. Use after building or changing UI, before claiming a page works, or when the user asks to test the frontend."
license: MIT
metadata:
  version: "0.4.0"
---

# webapp-testing

A passing unit test is not evidence that a page renders. Prove it in a browser.

## Order of preference
1. Playwright MCP tools if this session has them (Vibe exposes them as `<server>_<tool>`, e.g. `playwright_browser_navigate`). navigate → snapshot → click → screenshot.
2. `scripts/webcheck.mjs` from this skill when Playwright is in the repo or can be added.
3. Manual steps only as a last resort, and say explicitly that it was not automated.

## Steps
1. Read the dev command and port from AGENTS.md. Start the server in the background and poll until ready (`curl -sf http://localhost:PORT`); never use a fixed sleep.
2. Run: `node <skill-dir>/scripts/webcheck.mjs http://localhost:PORT/<route> --out .agents/artifacts`
3. Read the JSON: console errors, HTTP ≥400, **a11y violations (axe-core)**, missing accessible names, images without alt, horizontal overflow at 375px. Exit 1 means defects.
4. Open the screenshot. Check layout integrity, clipped text, placeholder content, and that empty / loading / error states exist.
5. Exercise the changed flow: fill, submit, navigate, go back. Assert on visible text, not DOM internals.
6. Fix defects in the code, never in the check.

## Rules
- Never claim a UI change works without a screenshot or a DOM assertion produced in this session.
- Test the states the spec names: empty, loading, error, long text, 375px and 1440px.
- Kill the server when done. Leave no background processes.
- Artifacts go to `.agents/artifacts/`; never commit them.

## Output
`route | states | console | network | a11y | verdict + artifact paths`

## write-plan

name: write-plan

# write-plan

A plan another agent could execute without you.

## Steps
1. Grep and read the files that already do something similar. Name existing files to modify and new files to create; if a name is unknown, write the pattern and say so.
2. Choose the most boring implementation that satisfies the spec. YAGNI: no abstraction for future needs.
3. Slice vertically: each task leaves the repo green (build + tests). A task that breaks the build and does not fix it is mis-cut.
4. Size: 1 task = 1 commit = 10–30 agent minutes = ≤3 files. More than 5 files means split.
5. Mark human checkpoints: migrations, public API changes, dependency changes, code deletion.
